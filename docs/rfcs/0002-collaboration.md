# RFC 0002 협업과 문서 작성 규약

- Status: Draft — 이 PR에서 팀의 적용 규칙으로 검토한다.
- 적용 대상: 팀원과 Claude Code·Codex. 훅 설치 전에도 사람이 따라야 할 작업 규칙이다.
- 근거: 팀의 README·후킹 설계 논의. RFC 0001은 회로 계약, 이 문서는 작업 규칙이다.

## DOC01 문서의 역할

| 문서 | 기록할 내용 | 기록하지 않을 내용 |
| --- | --- | --- |
| RFC | 지켜야 할 규약·룰, 적용 범위, 예외와 근거 | 이번 작업의 세부 구현 계획 |
| SPEC | What·Why·How로 작성한 기획 의도와 구현·검증 계획 | 기존 규약을 말없이 바꾸는 내용 |
| PR | 실제 변경, 이유, 구현 결과와 검증 근거 | 실행하지 않은 검사의 통과 주장 |

규약을 바꾸는 작업은 RFC 변경을 명시적으로 포함한다. SPEC만으로 규약을 덮어쓰지 않는다. 규약의 Draft·Accepted 상태와 구현 시험의 미실행·통과·실패는 구분한다. 문서 승인 여부는 사람이 결정한다.

## DOC02 SPEC을 먼저 확인하는 변경

코드·도구 설정·규약을 수정하기 전에 관련 SPEC과 RFC를 확인한다. 새 기능은 SPEC을 먼저 작성하고, 기존 동작 복구는 기존 SPEC을 참조할 수 있다. 다른 동작·구현 방향이면 해당 SPEC을 갱신한다. 일반 안내 문서의 오탈자 수정은 예외다.

SPEC은 관련 RFC 조항, 이번 변경에 적용되는 규칙, 규격 영향과 합격 조건을 적는다. 확인한 RFC 버전은 `docs/specs/index.json`의 SHA256으로 남긴다. 코드와 RFC가 바뀌면 관련 SPEC도 검토한다. SPEC의 존재만으로 설계가 타당하다고 판정하지 않는다.

SPEC의 How에는 대상 파일, 현재 구조, 변경 방법과 테스트를 적는다. 계획과 실행 결과를 구분한다. 코드에서 역작성한 SPEC은 기준 커밋과 코드에서 확인한 사실을 적고, 원래 작성자의 기획 의도나 시험 결과를 추정해서 단정하지 않는다.

## DOC03 사람이 읽을 수 있는 문장

- 익숙한 한국어와 실제 모듈·신호·파일 이름을 사용한다. 필요한 기술 용어는 처음에 설명한다.
- 불필요한 영어·약어와 새로 만든 추상적인 용어를 피한다. 한 문장에 한 주장을 적는다.
- 무엇이 언제 어떻게 달라지는지 적고, 사실·제안·미확정 사항을 구분한다.
- 예: '제어 경로의 정합성을 강화한다' 대신 '출력 중 IN_READY를 0으로 유지해 새 입력을 받지 않는다'고 쓴다.
- 단어 금지 목록으로 가독성을 채점하지 않는다. 사람 리뷰에서 이해되지 않는 설명을 고친다.

## DOC04 변경을 비교하는 그림과 코드

- 핵심 동작이 바뀌면 How에 짧은 수정 전후 코드 또는 diff와 동작 차이를 적는다.
- 블록·연결·처리 순서·상태가 바뀌면 '변경 전', '변경 후' 그림을 모두 제공한다.
- 코드 변경 PR의 How에 `흐름 변경: 있음` 또는 `흐름 변경: 없음`을 적는다. 없음이면 `시각화 생략 이유:`도 적는다. 있음이면 SPEC에 변경 전후 Mermaid 그림 두 개와 핵심 diff를 넣는다.
- 같은 블록은 같은 이름을 쓰고 추가·삭제·변경을 글자로도 표시한다. 시간 관계가 중요하면 에지표를 추가한다.
- 처음 역작성하는 모듈 SPEC에는 '현재 흐름'과 'RTL 변경 없음'을 적는다. 존재하지 않은 이전 설계를 만들지 않는다.
- 그림이 필요 없는 수정은 이유를 적는다. 그림과 코드가 맞는지는 사람이 검토한다.

## PR01 PR과 브랜치

- 작업 브랜치를 사용하고 원격 main에 직접 push하지 않는다. main의 삭제·강제 갱신도 금지한다.
- PR 본문은 정확히 `## What`, `## Why`, `## How` 제목을 사용하고 각 내용을 채운다.
- 코드 변경은 SPEC을 연결하고 How에 검사 명령·결과·미실행 사유를 적는다.
- 팀장과 관련 담당자에게 리뷰를 요청한다. 에이전트가 임의로 merge하지 않는다.
- 연속 PR은 앞 작업 브랜치를 기준으로 만들고 의존 관계를 본문에 적는다. 앞 PR 병합 후 기준 브랜치와 필요하면 커밋 이력을 정리한다.

## AUTO01 자동 검사와 리뷰의 책임

로컬 훅은 수정 전 확인과 명령 실행 전 검사를 맡는다. Git pre-push는 전송할 원격 ref를 보고 main 갱신을 차단한다. CI는 문서 형식·SPEC 연결·규약 버전 근거를 확인하며, 코드의 의미·문장 가독성·그림의 정확성은 사람이 검토한다.

로컬 확인은 이해의 증명이 아니다. 훅은 설치와 신뢰 설정이 필요하고, 외부 편집기·비활성화·미지원 도구를 모두 통제하는 보안 장치가 아니다. GitHub 브랜치 보호는 별도다. 검사 실패는 무엇이 빠졌고 어떻게 다시 진행할지 설명해야 한다.

## 적용과 예외

새 규약·SPEC·훅 자체를 처음 만드는 이번 PR은 기존 확인 기록이 없는 초기 설치 작업이다. 대화에서 합의한 기획을 먼저 SPEC 0001에 기록하고 구현한다. 이후 보호 대상 변경에는 설치된 훅을 적용한다. 예외를 늘릴 때는 이유와 검사 범위를 이 규약 및 SPEC에 남긴다. PDK·자격 증명·제한된 연구 자료는 커밋하지 않는다.
